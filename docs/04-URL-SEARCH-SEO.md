# URL, Scope, Search, and SEO

## Canonical route format

All path segments are lowercase. Trailing-slash policy must be consistent and enforced by redirects.

Implemented public and seller routes:

```text
/                                      public marketplace home
/markets/                               state/county finder
/tx/                                   statewide marketplace home
/tx/potter/                            county-context marketplace home
/tx/potter/listing/<uuid>/             public listing detail
/images/<uuid>/                        processed public listing image
/dashboard/
/dashboard/listings/new/               unified seller creation
/dashboard/listings/<uuid>/detail/     unified private owner detail
/dashboard/listings/<uuid>/edit/       unified owner editing
/staff/moderation/                      permission-protected moderation queue
/staff/reports/                         permission-protected report triage queue
```

The implemented canonical listing URL includes the listing’s actual state and
county plus its stable UUID. A title slug is not currently part of the route;
do not document redirect behavior that does not exist.

Do not use uppercase state routes in generated links. Uppercase state/county
aliases redirect to lowercase canonical paths; unknown or inactive contexts
return 404. Legacy typed seller routes remain compatibility workflows and are
not generated by the current dashboard or owner views.

## Context versus scope

The county in the URL provides **county context**. Per the stakeholder brief, the initial selected search scope remains statewide unless a buyer chooses county scope.

Represent the user’s explicit scope in a shareable query parameter:

```text
/tx/potter/?scope=state
/tx/potter/?scope=county
```

Rules:

- `scope=state` is the default when omitted.
- `scope=county` filters to the county in the route.
- Invalid scope values return a safe default and should not create indexable duplicate pages.
- Session persistence improves navigation convenience, but query parameters remain the source of truth for shared/search URLs.
- Search, filters, sort, pagination, and saved-search serialization use one normalized query object.

## Route resolution

Route lookup must:

1. resolve state by lowercase slug
2. resolve county within that state
3. require active/network-enabled location records where appropriate
4. redirect aliases to canonical slugs
5. return a true 404 for unknown locations rather than silently showing statewide content

No county creates infrastructure. Adding a county is reference/configuration data only.

## Search implementation

Phase 1 search remains in PostgreSQL.

### Text search

Public browse uses the accepted SRCH-003 PostgreSQL full-text document when
running on PostgreSQL, with a bounded SQLite `icontains` fallback for the test
path. County routes default to statewide scope; only `scope=county` narrows
results to primary and additional county placements. State routes have no
scope toggle. See `docs/features/SRCH-003-postgresql-full-text-search.md` for
the weighting, privacy, rollout, and query-plan contract.

The market finder (`/markets/`) and public state/county browse forms can
progressively request the same canonical GET URL with
`Accept: text/vnd.countypost.fragment+html`. The server returns only the
server-rendered result region for a valid request; a normal browser request
continues to return the full page. Finder requests are never made for blank
text, public form fields remain bounded by their Django forms, and pagination
links remain ordinary full-page GET links. The enhancement updates the
shareable query URL only after a successful fragment response. It does not
apply to registration, listing descriptions, reports, or other non-search
inputs.

- Build a weighted search document from title, description, city, category labels,
  published controlled/seller tags, make/model/brand, and approved vertical fields.
- Seller tags are searched only through the public selector after approval. Seller
  custom facts are not FTS/filter/sort input and never enter SEO, social metadata, or
  map queries.
- Prefer a persisted `SearchVectorField` with a GIN index once data volume makes query-time vectors inefficient.
- Do not add trigram/unaccent search until a measured need justifies it.
- Search only public-visible listing rows through the shared public selector.
- Rank first by relevance, then apply deterministic tie-breakers.

### Structured filters

Each vertical defines an allowlist of filters mapped to typed fields. Examples:

- homes: price, beds, baths, square feet, property type
- rentals: monthly rent, beds/baths, available date, pet policy
- autos: year, make, model, mileage, title status
- equipment: type, make, year, hours, condition
- cattle: species/breed/class, head count, weight or age range
- pasture: acreage, water, fencing, lease term
- home goods: type, brand, condition, working status

Do not construct ORM field paths directly from request strings. Parse request values into a typed filter object and map only approved fields/operators.

### SRCH-004 implementation

`PublicBrowseForm` now renders detail controls only for the selected supported
vertical. Homes, Rentals, Farm & Ranch equipment/pasture, Livestock, and Home
& Garden/Appliances use fixed typed-detail mappings; Autos retains its existing
controls. Cross-vertical, invalid, arbitrary, category/tag, profile-attribute,
and custom-fact parameters are dropped from the validated query object, so they
cannot enter chips, reset/pagination/live URLs, or ORM lookups. See
`docs/features/SRCH-004-typed-public-browse-filters.md`.

### Sorting

Initial sort options:

- newest
- price low to high
- price high to low
- featured/recommended where the ranking contract is defined

Every sort must include a stable final tie-breaker such as ID to prevent duplicate/missing rows across pages.

### Pagination

Begin with ordinary page-number pagination if query performance is acceptable. Keep page size bounded. Move to cursor pagination only if deep-page performance becomes a measured issue.

## Featured placement

Paid featured entitlement must not erase relevance or trust controls.

- Only active, unexpired, approved listings can be featured.
- Placement eligibility comes from `FeaturedPlacement`, not a request parameter.
- A deterministic policy defines where featured rows appear and how many can display.
- Sponsored/featured treatment should be visually clear.
- Expired/suspended listings are excluded even if a placement record remains.

## Index plan

Likely initial indexes:

- listing public visibility: status, published_at, expires_at
- location/category/status compounds based on actual query order
- seller/status for seller dashboard
- GIN search vector
- trigram indexes for selected text fields
- vertical range fields used by filters
- order and Stripe event external IDs
- outbox status/available_at

Use `EXPLAIN (ANALYZE, BUFFERS)` against realistic seeded data before adding speculative indexes. Every index has write and storage cost.

## SEO

### M10 implementation

- `/robots.txt` advertises `/sitemap.xml` and disallows private operational
  route prefixes.
- The sitemap index links to paginated state, county, and listing XML files.
  Each file contains at most 1,000 public URLs and streams its response.
- State and county sitemap entries require active, network-enabled geography;
  listing entries use `public_listings()` and therefore exclude inactive,
  expired, suspended, sold, draft, and otherwise non-public records.
- Clean directory routes have self canonicals. Search, filters, sorting, and
  pagination retain their usable query state but are `noindex,follow` and
  canonicalize to the clean route. Their `og:url` also uses that clean,
  query-free canonical. Pagination links expose `rel=prev`/`next`.
- Account, staff, billing, private-media, and draft URLs are not linked from
  sitemaps and must not gain public canonicals.
- Fragment responses are not standalone canonical documents and vary by
  `Accept`; their full-page query URLs retain existing `noindex,follow`
  behavior and clean-route canonicals.

### External maps privacy boundary

Public listing detail contains a lazy Google Maps iframe alongside
user-initiated Google Maps search and directions fallback links. The iframe
uses no API key or page-load JavaScript, has `referrerpolicy="no-referrer"`,
and makes a third-party request to Google only when the lazy frame loads.
Links open in a new window with `noopener noreferrer`. The default destination
is only public city, county, and state. An exact street/unit/postal address is
included only for the approved Home or Rental opt-in field when the seller
explicitly made it public. Private addresses, coordinates, and `general_area`
are never used as map destinations. No production CSP is currently configured;
before a restrictive CSP is activated, it must include
`frame-src https://www.google.com` while the iframe remains enabled.

Implemented public home, directory, market-finder, and listing pages use
deterministic title, description, canonical, Open Graph, and Twitter-card
metadata through an explicit presentation layer. Absolute social image URLs are
limited to ready processed listing renditions selected through the public
listing selector; no original upload, remote image, or fabricated brand image
is used. County-route metadata uses the imported county-equivalent display name
and state without adding a generic `County` suffix. Listing metadata contains
only title, city, state, and route facts:
it never includes private addresses, email, phone, `general_area`, coordinates,
listing description, draft/non-public media, or query strings. Listing cards
and gallery images emit known dimensions; browse cards and below-fold gallery
images use lazy loading/asynchronous decoding and request only processed
renditions. No JSON-LD is emitted.

Future listing-page enhancements should include only schema markup that can
satisfy all schema and privacy requirements across each supported vertical.

Browse/filter pages:

- index only curated state/county/category combinations that provide useful inventory
- canonicalize or `noindex` combinatorial filter URLs
- exclude account, checkout, moderation, search-result, and internal pages from indexing
- generate XML sitemaps for active listing detail pages and selected landing pages
- remove expired/suspended URLs from sitemaps promptly while returning an intentional detail/retention response

## Performance budget

The listing-card and listing-detail experience should be image-conscious:

- responsive derivatives
- explicit width/height to prevent layout shift
- lazy loading below the fold
- modern formats when processing supports them
- avoid loading original seller uploads on browse pages
- server-render useful content before enhancement scripts run
